## 背景与问题

### 当前 UI 的问题

v0.1 和 v0.2 实现了功能，但 **UI/UX 未从用户体验出发**，导致：

1. **界面丑**：没有设计系统，组件风格不统一，视觉上不像"产品"
2. **信息架构混乱**：技术细节直接暴露（如：Render Inspector、Tokenizer 调试），普通用户看不懂
3. **操作流程复杂**：想看"今日成本"需要点 3-4 次，效率低
4. **开发者视角，不是产品视角**：界面是"开发者给开发者用的工具"，不是"产品"
5. **发布阻碍**：界面丑 + 不好用 → 不敢发布给 GitHub 社区

### 为什么现在做

- **v0.3 计划发布到 GitHub**：必须先解决 UI/UX 问题，否则用户流失率高
- **建立第一印象**：GitHub 用户第一次打开 TokenAccountant，界面丑 → 直接关掉
- **差异化竞争**：虽然"没有真正的竞品"，但用户界面是建立信任的第一步

### 用户画像（重新定义）

**主要用户**：使用 token 中转站的人（开发者、小团队技术负责人）

**用户目标**：

- 🎯 "我想知道今天花了多少 Token"（Token 价格不同、中转配置不同、计价原则不同，所以我们把这个需求变成"每天花了多少 Token"）
- 🎯 "我想知道有没有被 Provider 坑"（审计可信度）→ 因此要同时记录中转返回信息里记录的、以及实际 detect 的
- 🎯 "我想快速切换 Provider"（易用性）

**用户技术水平**：

- 能配置 API Key、能看懂 JSON
- 但不想看到"Render Inspector"、"Tokenizer 调试"等技术细节

## 目标

### 产品目标

1. **从"工具"到"产品"**：界面美观、易用，让用户愿意 daily active use
2. **信息架构重构**：以用户目标为中心，而不是以技术实现为中心
3. **默认简洁，高级折叠**：普通用户看简洁视图，开发者自行展开高级选项
4. **建立信任感**：视觉设计专业，让用户信任审计结果
5. **为发布做准备**：v0.3 达到"可发布到 GitHub"的质量标准

### 业务目标

- 以 GitHub star 为准：作为个人第一个项目，目标收获 100 ⭐
- 建立"Token 透明化"的心智定位（不是"成本工具"，是"Token 审计工具"）

---

## 非目标 (Non-goals)

**v0.3 明确不做的事情**：

1. ❌ **不做多用户/团队管理**：仍然是单用户应用
2. ❌ **不做复杂的自定义**：不支持主题切换、布局自定义等
3. ❌ **不做移动端适配**：仅支持桌面端（macOS/Windows/Linux）
4. ❌ **不做多语言支持**：仅支持中文/英文（发布到 GitHub，英文是标配）
5. ❌ **不做新的审计功能**：UI 重构不涉及底层逻辑变更（审计精度在另一个 PRD）
6. ❌ **不强调"成本"**：因为中转站配置不同、计价原则不同，所以聚焦"Token 统计"而不是"成本计算"

## 用户故事

### 核心用户故事

**作为开发者**，我希望能够：

1. **一眼看到每日 Token 统计**

   - 作为开发者，我希望打开应用后，首页直接显示最近 7 天 Token 统计（Input / Cache / Output），以便我快速了解 Token 消耗情况
   - 作为开发者，我希望看到"今日 Token 消耗"和"本月 Token 消耗"，以便我预测使用趋势
2. **快速查看审计记录**

   - 作为开发者，我希望在首页就能看到"可疑请求数"，以便我快速发现异常
   - 作为开发者，我希望点击"可疑请求"后，直接看到详情（哪次请求、Claimed vs Detected 差异多少、原因是什么），以便我快速判断是否需要争议
3. **简单管理 Provider**

   - 作为开发者，我希望在"设置"里快速切换活跃 Provider，以便用不同的中转站
   - 作为开发者，我希望看到 Provider 配置细节，因为 Provider 的设置会被用来覆盖 Claude 的设置，所以我希望确认配置是否正确
   - 作为开发者，我希望用一个统计面板看到"审计 Token 数" vs "声称 Token 数"的差异率，以便我快速判断 Provider 的可信度
4. **隐藏开发者选项**

   - 作为开发者，我希望"Render Inspector"等高级功能默认隐藏，以便界面简洁
   - 作为开发者，我希望在"设置 → 开发者模式"里能展开这些功能，以便我调试

## 功能需求

### 1. 信息架构重构

**描述**：重新组织导航结构，以用户目标为中心。

**当前架构**（基于 v0.1/v0.2 代码）：

```
Tab 1: Providers (技术细节暴露)
Tab 2: Proxy (启动/停止)
Tab 3: Audit Logs (纯表格，无可视化)
Tab 4: Settings (所有设置混在一起)
```

**目标架构**（以用户目标为中心）：

```
[🏠 Dashboard]  ← 新增！默认首页
  - 最近 7 天 Token 统计（Input / Cache / Output）
  - 今日 Token 消耗、本月 Token 消耗
  - 可疑请求数
  - 快速操作（启动代理、切换 Provider）

[Audit Logs]  ← 重构！列表 + 详情弹窗 + 趋势图
  - 列表（时间、模型、Claimed Tokens / Detected Tokens、差异率、可疑标记）
  - 筛选（按日期、Provider、可疑状态）
  - 详情弹窗（Claimed vs Detected 全文对比）
  - 趋势图（按日/周/月查看 Token 消耗）

[Providers]  ← 简化！配置细节 + 统计面板
  - 列表（名称、类型、状态）
  - 快速切换（一键切换活跃 Provider）
  - 配置细节卡片（显示 API Base URL、覆盖的 Claude 设置）
  - 统计面板（审计 Token 数 vs 声称 Token 数、差异率）
  - 高级选项（折叠）：API Key、自定义参数

[Settings]  ← 重组！基础设置 + 开发者模式
  - 基础设置（端口、语言）
  - 开发者模式（开关）：展开后显示 Render Inspector、Tokenizer 调试
  - 关于（版本号、GitHub 链接、Changelog）
```

**验收标准**：

- 用户能在 **10 秒内**找到"今日 Token 消耗"
- 用户能在 **3 次点击内**完成"切换 Provider"
- 开发者模式默认关闭，需要主动开启

### 2. Dashboard 首页（新增）

**描述**：新增 Dashboard 作为默认首页，让用户一眼看到 Token 统计。

**功能点**：

| 功能            | 说明                                          | 优先级 |
| --------------- | --------------------------------------------- | ------ |
| 今日 Token 卡片 | 显示今日 Token 消耗（Input / Cache / Output） | P0     |
| 本月 Token 卡片 | 显示本月累计 Token 消耗 + 趋势箭头            | P0     |
| 可疑请求数      | 显示今日/本月的可疑请求数（红色高亮）         | P0     |
| Token 趋势图    | 过去 7 天的 Token 消耗趋势（折线图）          | P0     |
| 快速操作        | 启动/停止代理、切换 Provider                  | P1     |
| 最近审计记录    | 显示最近 5 条审计记录（可点击查看详情）       | P1     |
| 模型使用分布    | 饼图：哪个模型用得最多                        | P2     |

**UI 设计建议**：

- 卡片式布局（参考：Stripe Dashboard、Vercel Dashboard）
- 颜色编码：🟢 正常（差异 < 3%）、🟡 警告（3-5%）、🔴 异常（> 5%）
- 响应式布局：窗口大小变化时，卡片自动调整位置
- **不显示"成本"**：因为中转站配置不同，计价原则不同，所以只显示 Token 数

**验收标准**：

- Dashboard 加载时间 < 1 秒（数据从 SQLite 读取）
- Token 数字实时更新（代理运行时，每 10 秒刷新一次）

### 3. Audit Logs 重构

**描述**：从"纯表格"变成"列表 + 详情弹窗 + 趋势图"，**同时显示 Claimed vs Detected**。

**功能点**：

| 功能     | 说明                                                                 | 优先级 |
| -------- | -------------------------------------------------------------------- | ------ |
| 列表视图 | 显示所有审计记录（时间、模型、Claimed / Detected、差异率、可疑标记） | P0     |
| 筛选器   | 按日期、Provider、模型、可疑状态筛选                                 | P0     |
| 搜索     | 按请求 ID 或 session ID 搜索                                         | P1     |
| 排序     | 按时间、Token 数、差异率排序                                         | P1     |
| 详情弹窗 | 点击某行，弹窗显示 Claimed vs Detected 详细对比                      | P0     |
| 趋势图   | 按日/周/月查看 Token 消耗趋势（Claimed vs Detected 双线图）          | P1     |
| 导出     | 导出 CSV / JSON（包含 Claimed 和 Detected 数据）                     | P2     |

**验收标准**：

- 列表加载 1000 条记录 < 1 秒
- 详情弹窗打开时间 < 200ms
- 趋势图渲染时间 < 500ms
- **Claimed vs Detected 数据完整**（不从审计记录中遗漏）

### 4. Providers 简化 + 统计面板

**描述**：从"完整 CRUD"变成"简化视图 + 配置细节 + 统计面板 + 高级选项折叠"。

**功能点**：

| 功能                  | 说明                                                                 | 优先级 |
| --------------------- | -------------------------------------------------------------------- | ------ |
| 列表视图              | 显示所有 Provider（名称、类型、状态）                                | P0     |
| 快速切换              | 一键切换活跃 Provider（不需要进入详情页）                            | P0     |
| 配置细节卡片          | 显示 API Base URL、覆盖的 Claude 设置（如：API Version、Max Tokens） | P0     |
| 统计面板              | 显示该 Provider 的审计 Token 数 vs 声称 Token 数、差异率             | P0     |
| 添加 Provider（简化） | 只填"名称"、"API Key"、"模型"                                        | P0     |
| 高级选项（折叠）      | API Base URL、Tokenizer 类型、自定义参数                             | P1     |
| 编辑/删除             | 长按或右键菜单                                                       | P1     |

**UI 设计建议**：

- Provider 卡片：显示 logo（OpenAI/DeepSeek/Claude）、名称、状态（🟢 活跃 / ⚪ 未激活）
- 快速切换：点击卡片即可切换，不需要进入详情页
- 配置细节卡片：明确显示"此 Provider 会覆盖 Claude 的以下设置：XXX"
- 统计面板：显示"审计 Token 数 vs 声称 Token 数"的对比图（双条形图）
- 高级选项：点击"高级"才展开（默认折叠）

**统计面板内容**：

```

│  - Reason: Tokenizer mismatch        │
└─────────────────────────────────────────┘
```

**验收标准**：

- 用户能在 **1 次点击内**切换活跃 Provider
- 添加 Provider 的表单字段 **≤ 5 个**（不包含高级选项）
- 统计面板数据实时更新（代理运行时，每 10 秒刷新一次）

## 非功能需求

### 性能

- Dashboard 加载时间 < 1 秒（数据从 SQLite 读取）
- Audit Logs 列表加载 1000 条记录 < 1 秒
- 详情弹窗打开时间 < 200ms
- 趋势图渲染时间 < 500ms
- 统计面板数据刷新时间 < 10 秒（代理运行时）

### 可靠性

- UI 崩溃率 < 0.1%（发布后监控）
- 数据加载失败时，有明确的错误提示和重试按钮
- 网络断开时（如果未来有云端同步），有离线模式

### 兼容性

- macOS 12+、Windows 10+、Linux（Ubuntu 20.04+）
- 屏幕分辨率：最小 1280x720（720p），推荐 1920x1080（1080p）

### 可访问性

- 配色方案通过无障碍测试（对比度 > 4.5:1）
- 所有交互元素支持键盘操作（Tab、Enter、Space）
- 图片/图标有 alt text（屏幕阅读器友好）

## 风险与缓解

### 技术风险

| 风险                     | 影响 | 缓解措施                                                   |
| ------------------------ | ---- | ---------------------------------------------------------- |
| 重构导致功能回归         | 高   | 自动化测试覆盖核心流程（添加/切换 Provider、查看审计记录） |
| 性能退化（趋势图渲染慢） | 中   | 使用虚拟滚动（Virtual Scrolling）+ 数据分页                |
| 设计系统不一致           | 中   | 建立 Component Library（Storybook），确保复用              |
| Token 统计不准确         | 高   | 与审计精度 PRD 协同，确保 Detected Token 数准确            |

### 产品风险

| 风险                         | 影响 | 缓解措施                                             |
| ---------------------------- | ---- | ---------------------------------------------------- |
| 用户不喜欢新设计             | 高   | 发布前进行可用性测试（5 名用户）                     |
| 重构范围蔓延（想做更多功能） | 中   | 严格遵守 Non-goals，只做 UI/UX 重构                  |
| 发布延迟                     | 中   | 拆分任务，优先做 P0 功能                             |
| 用户不理解"Token 统计"       | 中   | 提供 Tooltip 说明（"为什么显示 Token 而不是成本？"） |

### 数据记录原则

**Claimed vs Detected 双记录**：

- **Claimed Tokens**：Provider 在 API 响应中返回的 Token 数（可能不准确）
- **Detected Tokens**：TokenAccountant 使用 Tokenizer 本地计算的 Token 数（更准确）
- **差异率**：`|Claimed - Detected| / Claimed * 100%`
- **用途**：用户可以用这个数据判断 Provider 是否"虚报" Token 数，用于争议账单
