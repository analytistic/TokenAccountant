## 背景与问题

### 当前精度问题

v0.2 的审计功能已实现，但**精度不足，与官方 API 差异达 25%**。

**问题表现**：
- 用户（开发者）发现 TokenAccountant 计算的 Token 数与 Provider 返回的 Token 数差异巨大（25%）
- 导致审计结果不可信，用户不敢用审计结果去争议 Provider 账单
- 核心价值链断裂："审计"功能失去意义

**根本原因分析**（技术团队初步诊断）：
1. **使用基础分词器**：当前使用 tiktoken 的 `cl100k_base` 等通用 tokenizer，未使用模型厂商提供的官方 `tokenizer.json`
2. **词表未对齐**：不同模型的 tokenization 逻辑不同（GPT-4o vs Claude 3.5 vs DeepSeek-V4），通用 tokenizer 无法精确匹配
3. **特殊 token 处理不一致**：BOS/EOS/PAD token 的处理方式与官方实现不符
4. **多模态缺失**：图片等多模态内容的 Token 计数完全未实现

### 为什么现在做

- **核心价值崩塌**：如果审计精度不够，TokenAccountant 的差异化价值（"审计"）就不存在了
- **发布前必须解决**：计划 v0.3 后发布给 GitHub 社区，精度问题是阻塞项
- **用户信任建立**： only way to build trust is "审计结果可验证"

### 用户画像（ revisité）

**主要用户**：开发者、小团队技术负责人
- 关心成本，希望审计结果准确
- 有技术能力验证 Token 计数（对比官方 API）
- 如果发现精度差，会立即弃用

## 目标

### 产品目标

1. **提升审计精度**：将 Token 计数差异从 25% 降到 **< 5%**（目标 < 3%）
2. **覆盖主流模型**：支持 GPT-4o、Claude 3.5、DeepSeek-V4、Gemini 1.5
3. **建立信任**：让用户看到"精度对比报告"，愿意信任审计结果
4. **为发布做准备**：精度达标后，发布 v0.3 到 GitHub

### 业务目标

- **可信度提升**：用户愿意用审计结果去争议 Provider 账单
- **发布准备**：v0.3 达到"可发布给社区"的质量标准
- **建立技术壁垒**：官方 tokenizer 支持是竞品难以快速复制的

---

## 非目标 (Non-goals)

**v0.3 明确不做的事情**：

1. ❌ **不做所有模型**：仅支持主流模型（GPT-4o、Claude 3.5、DeepSeek-V4、Gemini 1.5），其他模型标记为"实验性"
2. ❌ **不做多模态完整支持**：v0.3 先支持图片 Token 计数（简单估算），不做视频/音频
3. ❌ **不做自动精度修复**：精度问题需要技术团队手动适配每个模型，不做"自动学习"
4. ❌ **不重新设计审计管道**：v0.2 的审计逻辑保留，只替换 tokenizer 层
5. ❌ **不做新的 UI 功能**：精度提升是底层改进，UI 不变（UI 重构在另一个 PRD）

## 用户故事

### 核心用户故事

**作为开发者**，我希望能够：

1. **信任审计结果**
   - 作为开发者，我希望 TokenAccountant 计算的 Token 数与官方 API 差异 < 5%，以便我敢用这个结果去争议账单
   - 作为开发者，我希望看到"精度对比报告"（TokenAccountant vs 官方），以便我验证审计结果的准确性

2. **支持我使用的模型**
   - 作为开发者，我希望 TokenAccountant 支持我正在用的模型（GPT-4o、Claude 3.5、DeepSeek-V4），以便我能审计所有请求
   - 作为开发者，我希望对于不支持的模型，系统明确提示"精度可能不准"，以便我决定是否信任结果

3. **理解精度差异的原因**
   - 作为开发者，我希望在"可疑请求"中看到"精度差异原因"（如："使用了通用 tokenizer，未加载官方 tokenizer.json"），以便我理解为什么差异大

## 功能需求

### 1. 官方 Tokenizer 加载

**描述**：从 HuggingFace 或模型厂商 GitHub 下载官方 `tokenizer.json`，使用 `tokenizers` crate 加载。

**功能点**：

| 功能 | 说明 | 优先级 |
|------|------|--------|
| 下载官方 tokenizer.json | 从 HuggingFace Hub 或厂商 GitHub 下载 | P0 |
| 缓存 tokenizer 文件 | 下载后缓存到本地，避免每次启动都下载 | P0 |
| 加载 tokenizer | 使用 `tokenizers` crate 加载 `tokenizer.json` | P0 |
| 回退机制 | 如果官方 tokenizer 下载失败，回退到通用 tokenizer 并标记"精度可能不准" | P0 |
| 版本管理 | 支持 tokenizer 版本更新（如：GPT-4o 的 tokenizer 更新了） | P1 |

**支持模型列表（P0）**：

| 模型 |Tokenizer 来源 | 状态 |
|------|----------------|------|
| GPT-4o | HuggingFace: `Xenova/gpt-4o-tokenizer` | 待实现 |
| Claude 3.5 Sonnet | Anthropic 官方 GitHub | 待实现 |
| DeepSeek-V4 | DeepSeek 官方 GitHub | 待实现 |
| Gemini 1.5 Pro | Google AI Studio 文档 | 待实现 |

**验收标准**：
- 官方 tokenizer 加载成功率 > 99%
- 回退到通用 tokenizer 时，UI 明确提示"精度可能不准"
- tokenizer 文件缓存到 `~/.tokenaccountant/tokenizers/`

### 2. Token 计数精度提升

**描述**：使用官方 tokenizer 重新实现 Token 计数逻辑，确保与官方 API 返回值差异 < 5%。

**功能点**：

| 功能 | 说明 | 优先级 |
|------|------|--------|
| Input Token 计数（官方 tokenizer） | 使用官方 tokenizer 计算 Input Token 数 | P0 |
| Output Token 计数（官方 tokenizer） | 使用官方 tokenizer 计算 Output Token 数 | P0 |
| 特殊 token 处理 | 正确处理 BOS/EOS/PAD token | P0 |
| Tool Calling Token 计数 | 正确处理 tool calls 的 Token 消耗 | P0 |
| Thinking Mode Token 计数 | 正确处理 DeepSeek 的 thinking blocks | P1 |
| 图片 Token 计数（估算） | 简单估算图片的 Token 数（如：1 张图 = 85 tokens） | P1 |
| 多模态（视频/音频） | 标记为"不支持"，返回 0 | P2 |

**精度标准**：

| 模型 | 目标差异 | 验收标准 |
|------|---------|---------|
| GPT-4o | < 3% | 测试 100 条真实请求，平均差异 < 3% |
| Claude 3.5 Sonnet | < 3% | 测试 100 条真实请求，平均差异 < 3% |
| DeepSeek-V4 | < 5% | 测试 100 条真实请求，平均差异 < 5% |
| Gemini 1.5 Pro | < 5% | 测试 100 条真实请求，平均差异 < 5% |

**验收标准**：
- 所有 P0 模型的精度达标（差异 < 5%）
- 精度对比报告可导出（JSON 格式，包含每次测试的详细数据）

### 3. 精度验证框架

**描述**：建立自动化测试框架，持续验证 Token 计数精度。

**功能点**：

| 功能 | 说明 | 优先级 |
|------|------|--------|
| 测试用例库 | 收集真实请求样本（覆盖不同模型、不同消息类型） | P0 |
| 自动化测试 | CI/CD 中自动运行精度测试 | P0 |
| 精度报告生成 | 每次测试生成精度报告（Markdown 格式） | P0 |
| 回归检测 | 如果某次提交导致精度下降 > 1%，CI 失败 | P1 |
| 可视化报告 | 生成精度趋势图（每次版本对比） | P2 |

**测试用例库结构**：
```
test_cases/
├── gpt-4o/
│   ├── simple_conversation.jsonl  # 简单对话
│   ├── tool_calling.jsonl         # Tool calling
│   ├── multi_turn.jsonl          # 多轮对话
│   └── with_image.jsonl         # 含图片
├── claude-3.5-sonnet/
│   └── ...
└── deepseek-v4/
    └── ...
```

**验收标准**：
- 测试用例库覆盖 P0 模型的主要使用场景
- CI/CD 自动化测试通过率 > 95%
- 精度报告可在 GitHub Actions 中查看

### 4. 精度差异提示（UI）

**描述**：当系统使用通用 tokenizer（精度可能不准）时，UI 明确提示用户。

**功能点**：

| 功能 | 说明 | 优先级 |
|------|------|--------|
| 精度状态指示器 | 在审计记录中显示"精度状态"（精确 / 大致精确 / 不精确） | P0 |
| 差异原因标注 | 在"可疑请求"中标注差异原因（如："未使用官方 tokenizer"） | P0 |
| 精度对比报告查看 | 用户可查看详细的精度对比报告 | P1 |
| 模型支持状态查看 | 在 Provider 管理页显示"该模型的 tokenizer 支持状态" | P1 |

**UI 设计建议**：
- 精度状态用颜色区分：🟢 精确（差异 < 3%）、🟡 大致精确（3-5%）、🔴 不精确（> 5%）
- 在审计记录列表中，精度状态显示为列（可排序）

**验收标准**：
- 用户能清晰看到每次请求的"精度状态"
- 当用户使用不支持的模型时，系统明确提示"精度可能不准"

## 非功能需求

### 性能

- 加载官方 tokenizer 的时间 < 500ms（从本地缓存加载）
- Token 计数计算时间 < 100ms（对于 4096 tokens 以内的请求）
- 下载 tokenizer.json 的时间 < 5 秒（取决于网络）

### 可靠性

- tokenizer 加载失败时有明确的错误提示
- 回退到通用 tokenizer 时，不影响代理服务器的正常运行
- 测试用例库持续维护（每次模型更新后，更新测试用例）

### 安全性

- 从 HuggingFace 下载 tokenizer.json 时，验证文件完整性（SHA-256 校验）
- 不将用户的 API Key 或请求内容发送到外部（tokenizer 下载不涉及用户数据）

### 兼容性

- 支持 macOS 12+、Windows 10+、Linux（Ubuntu 20.04+）
- 支持所有主流模型的官方 tokenizer 格式（HuggingFace `tokenizer.json`）

## 风险与缓解

### 技术风险

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 官方 tokenizer 下载失败（网络问题） | 高 | 提供离线安装包，用户可手动下载后放入缓存目录 |
| Tokenizer 格式不兼容 | 中 | 抽象 Tokenizer 层，支持多种格式（HuggingFace、Anthropic 自定义格式等） |
| 精度仍不达标（差异 > 5%） | 高 | 逐个模型调试，分析差异原因（特殊 token、BOS/EOS 等） |
| 性能退化（加载 tokenizer 慢） | 中 | 使用本地缓存，避免每次启动都下载 |

### 产品风险

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 用户仍不信任审计结果 | 高 | 提供"精度对比报告"，让用户自己验证 |
| 支持的模型太少 | 中 | 明确标注"实验性"模型，让用户选择是否信任 |
| 测试用例不足 | 中 | 鼓励社区贡献测试用例（GitHub Issues） |

## 附录

### 技术方案概览

```
当前架构：
Request → Message Converter → Tiktoken (通用 tokenizer) → Token 计数 → 审计记录

v0.3 目标架构：
Request → Message Converter → TokenizerFactory
                                    ├─ 官方 Tokenizer (tokenizers crate)
                                    └─ 通用 Tokenizer (tiktoken-rs) [回退]
                              → Token 计数 → 审计记录
```

### 精度验证流程

1. 准备测试用例（真实请求 + 官方 API 返回的 Token 数）
2. 运行 TokenAccountant，拦截相同请求
3. 对比：TokenAccountant 计算结果 vs 官方 API 返回值
4. 生成精度报告（差异百分比、差异原因）
5. 如果差异 > 5%，标记为"不精确"，需要调试
